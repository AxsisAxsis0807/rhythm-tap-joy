## 入力ソースと内部状態

`tests/botplay-boundaries.test.ts` はテスト内だけで `Reflect.get` を使い、既存privateフィールドを読み取る。本番APIの追加・可視性変更はない。

- 各境界フレームで、`sources` のID・レーン、`heldNotes` のノーツIDとholding、`holdStartedAt` のID・開始時刻を照合。
- `successfulHoldIds` と `heldIntervals` は終了済みホールドだけを含み、各保持区間の始点・終点・completedが譜面と一致することを検証。
- 全完了後、`sources` / `heldNotes` / `holdStartedAt` は空。成功IDと保持区間はホールド数に一致する。繰り返しadvanceとcompleteでも二重登録しない。
- 別の同一レーンソースが残るrelease/cancelの早期returnは、レーンの保持を継続する既存仕様。終了済みホールドのソース解放でも、保持中ホールドのソースを先に解放する人工的なケースでも、残りのソースとadvanceが正常終了まで保持する。
- 最後のソースを早期解除すると既存判定どおりMISSになり、privateマップも掃除される。BOT用の甘い早期解除判定はない。

## 同時刻イベントの監査

既存コードの順序は変更していない。

1. 元譜面の時刻順でpress/releaseのエッジを作り、時刻で安定ソートする。
2. 各入力の直前に、そのエッジの**譜面時刻**でadvanceする。全体の現在時刻で先にauto-MISSする順序にはしない。
3. 入力は譜面時刻からoffsetを引いてprocessへ渡す。process側だけが入力offsetを加える。
4. タップは固有ソースでpress→release。保持終点では直前のadvanceが正常終了を処理してからreleaseする。
5. 元譜面の同時刻記述順を逆にしたテストでも得点・全ノーツ判定・保持終了・掃除が同じ。
6. 全エッジが単調な譜面時刻順であること、全pressがPERFECTであること、ソースが重複せずpress/release各1回であることをイベントトレースで検証。

結果遷移の既存条件は `songTime > max(audioDuration, lastTail - offset + 2.5)`。境界ちょうどではplaying、その1ms後ではfinishedを確認した。仕様を変更していない。
